# Drivers

Most cameras need only a profile (one JSON file in `public/cameras/`). A **driver** is for a camera
type that needs code: a special frame format to decode, its own controls, readouts drawn over the
image. Example: `infiray-thermal/` turns the raw frames of InfiRay-style thermal cameras into
colours and temperatures.

**One driver = one folder here**, `public/drivers/<id>/`. Everything the camera type needs lives in
that folder: code, styles, tests, notes. Nothing in the app has to change. The app finds drivers
on its own (`drivers/index.json` is generated by `npm run dev` and `npm run build`), and a profile
picks one with:

```json
"driver": { "id": "infiray-thermal", "options": { "divisor": 64 } }
```

A broken driver never breaks the app: `npm run check` reports it, the app skips it with a console
warning, and any error thrown inside a driver is caught and logged.

## Folder layout

```
public/drivers/<id>/
  driver.js     required: export default { … } (below)
  style.css     optional, listed in `styles`; loaded only while the driver is active
  test.mjs      optional; `npm test` runs it with Node (exit code ≠ 0 = failed)
  README.md     recommended: what it supports, its options, what was tested
  …             any other modules it imports with relative paths
```

Folders starting with `_` are ignored; `_example/` is a small working driver to copy.

## driver.js

```js
export default {
  apiVersion: 1,
  id: 'my-camera',                  // equal to the folder name
  name: 'My camera',                // shown in the Camera tab
  description: 'What it handles.',
  kinds: ['thermal'],               // optional: profile kinds it is meant for (checked by npm run check)
  styles: ['style.css'],            // optional
  probeModes: [[256, 192]],         // optional: extra sizes the compatibility test should try
  validateOptions(options) { return []; },   // optional: problems with profile.driver.options
  suggest({ kind, modes, device }) { return null; },  // optional, see below
  create(ctx) { return { /* instance hooks */ }; },  // required
};
```

The top-level module must not touch the DOM: `npm run check` imports it in Node to read this
object. Use the DOM only inside `create()` and the instance.

`suggest()` lets the compatibility test put your driver into the draft profile it generates.
`modes` are the native modes it measured (`{ width, height, frameRate }`). Return
`{ options, defaultMode }` if the camera looks like yours, otherwise `null`.

### ctx: what the app gives a driver

| | |
|---|---|
| `profile`, `options` | the camera profile, and `profile.driver.options` (or `{}`) |
| `panel` | an empty element at the top of the Image tab for your controls |
| `frameLayer` | an element exactly over the displayed image (pointer events off), for marks |
| `viewerLayer` | an element over the whole viewer, for legends and tooltips |
| `prefs.get(defaults)`, `prefs.set(values)` | settings saved in the browser, per driver |
| `frameSize()` | `{ width, height }` of the displayed image in CSS px |
| `sourceToFrame(x, y, w?, h?)` | position on screen (or in a `w`×`h` picture) of a pixel of the image you returned; follows rotation, mirroring and zoom |
| `frameToSource(x, y, w?, h?)` | the inverse |
| `isFrozen()` | whether the user froze the image |
| `show(image)` | put an `ImageData`/canvas on screen now (e.g. re-colour a frozen frame) |
| `refresh()` | ask the app to call your `layout()` and `hud()` again |
| `saveFile(blob, name)` | save to the user's folder or download |
| `fileName(prefix, ext)` | a timestamped file name |
| `toast(message)` | a short message at the bottom of the screen |

The panel can use the app's CSS building blocks: `h3`, `.field`, `.row`, `.check`,
`.chips`/`.chip` (with `aria-pressed`), `.segmented` (buttons with `aria-pressed`), `.btn small`,
`.muted small`.

### The instance returned by create(): all hooks optional

| Hook | Called | Return |
|---|---|---|
| `processFrame(video)` | for each new camera frame (frames are dropped while the previous call is still running); may be `async` | an `ImageData` or canvas to show instead of the video, or `null` to show the video |
| `layout()` | after each frame, and when the view is resized, rotated, mirrored or zoomed | — draw into `frameLayer` / `viewerLayer` |
| `hud()` | with `layout()` | text for the info bar over the image, or `''` |
| `pointer(info)` | when the pointer moves over the image; `null` when it leaves | — `info` has `frameX/Y`, `sourceX/Y` (in your image's pixels) and `viewerX/Y` |
| `photo(canvas)` | when the user takes a photo; `canvas` is what the screen shows | a canvas to save instead, or `null` |
| `destroy()` | when the camera or its profile changes | — the app clears `panel` and the layers itself |

Filters, rotation, zoom, photos and recording work on whatever `processFrame` returns, so a driver
only deals with its own camera.

## Checking a driver

1. `npm run check`: the driver's shape, and the options of every profile that uses it.
2. `npm test`: your `test.mjs`, if any. Test pure logic (decoding, maths) with synthetic data so it
   runs without the camera; see `infiray-thermal/test.mjs`.
3. `npm run dev` with the camera connected, in Chrome or Edge.
